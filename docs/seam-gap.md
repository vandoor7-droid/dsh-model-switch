# Missing official seams

Official DSH is a read-only dependency. This plugin degrades on a clean tag when a seam is absent.

## Replacing a bundled capability row at runtime

- **Needed for:** handing the single `permissionPresets.registerAuto` slot over without a Host restart when the official `auto-review` row is already active — the hot-install window (disable → remove → install → enable) that 0.4.31's takeover cannot always close inside its retry budget.
- **Where used:** `src/auto-review-takeover.ts` (`reclaimOfficialAutoReviewRow`, `scheduleLateReclaims`), `src/auto-review.ts` (`installToolCallSafetyNet`).
- **What exists:** `loader/patch-context` (a synchronous waterfall), `Entry.update({ disabled: true })`, `loader/partial-dispose`, and the single-registration `registerAuto`. Disabling a row *starts* its fiber's disposal; the loader does not await it, so a reclaim either retries (now ~3 s plus three late re-claims) or leaves the official row serving unguarded until the next loader cycle.
- **Handling:** retry as above, and shield the call: a prepended `tools/pre-execute` listener on this row's own context returns `{ kind: 'allow' }` for **seam** failures only, and only while this row knows it does not hold the route. Reviewer transport/quota errors stay fail-closed.
- **Upstream:** a public "supersede this bundled row" declaration (or a `registerAuto` that reports and waits for its predecessor's release) would remove the window entirely; a loader API that can address rows nested in a preset's `config.plugins` would let a plugin displace a nested official row instead of only reporting it. Until then the shield plus the actionable restart log is the documented behavior.

## Goal creation from a client slot

- **Needed for:** arming a reviewed Plan as the session's goal before its review is answered, so `dsh-goal-round-driver` carries the Plan after plan mode exits.
- **Where used:** `src/picker/plan-goal.ts`, `src/client/picker/PlanReviewCard.tsx`, `src/client/picker/install.tsx`.
- **Status: released, though DSH's own surface deliberately does not use it.** `@deepseek-ai/dsh-goal` publishes `remote.goals.create` (`@Remote('create') remoteExportCreate`, resolved from the wire session identity) and `@deepseek-ai/dsh-api-remotes` wires it into the generated client face — its own e2e calls `client.remote.goals.create(rootAgent.id, { objective: 'root goal' })`. DSH's shipped `dsh-client-ui-goal` nevertheless documents *Goal creation remains outside this package* and routes only `get` / `edit` / `pause` / `resume` / `clear`, leaving `/goal <objective>` as the human creation path.
- **Handling:** the card drives `create` (and, to replace an unfinished goal, `get` + `clear`) through a structurally typed face resolved **per render** with `ctx.get('remote.goals', false)` — never through this plugin's static `inject` list, because a dotted-service inject would block the whole client plugin on a deployment that mounts no goal package. Absent the service the action reports `unsupported` and disables itself while every other Plan Review action keeps working.
- **Upstream:** nothing to request while the remote stays published; if a future Host drops `create` from the client face, `setPlanAsGoal` already reports `unsupported`. Recorded for the roadmap: a programmatic create entry in the shipped goal surface would let plugins set a goal without probing the remote face themselves.

## `session.selectModel` default-write ordering

- **Observation:** `session.selectModel` persists the Session selection as the deployment default alongside the Session-only switch. On `0.1.2-alpha.4` the controller awaited `agentDefaultModel.saveSelection(selected)` before resolving `selectModel`; on `0.2.0-rc.2` the same step is fired, not awaited (`void this.ctx.agentDefaultModel.saveSelection(selected).catch(…)`, `packages/api/session-controller/src/commands.ts`, `selectModel`), so the RPC resolves *before* the namespace revision moves and no `captured + 1` revision fence can be assumed.
- **Handling (0.4.23+):** the plugin no longer compensates this write at all. Its Main-default card, the pre-switch capture, the revision-fenced restore (`main-default-restore.ts`, removed), and the picker's gate on a writable Main ConfigForm were deleted in 0.4.23: the deployment default is simply allowed to drift to the last session switch, exactly like a native TUI switch, and a fixed default is configured on DSH's own Models page. The projection itself stayed useful — since 0.4.23 the plugin watches the session's `model/selection` projection (same event, sole emitter `selectModel`) to apply provider capability groups on every switch surface. No Core patch.
- **Upstream:** the ordering is still not part of the released contract. A published Session-only selection entry point (a switch that does not persist the deployment default) would let a plugin offer true session-local switching again; until then the drift is the documented behavior, not a bug to fence.

## `session/writer-held` on a resumed Session

- **Observation:** the Host maps an in-process/lease `SessionAlreadyOwnedError` to `RemoteError('session/writer-held')` when a Session is created, adopted, or resumed for write (`packages/api/session-controller/src/agent.ts` `resolve`, `commands.ts` `rejectCreation`), and official clients render `error.sessionInUse` for it. A second frontend attached to the same Session is the documented cause.
- **Handling:** this plugin does not interpret, mask, or retry that code. Every action it performs keeps the code visible (`planErrorText`), and a takeover is never left with every action disabled, so the human can always act on it.
- **Upstream:** nothing to request here — the seam is a Host ownership decision, not a missing interface.

## `ctx.settingsScope` on non-loopback browsers

- **Needed for:** the durable Model Switch settings namespace on the trusted lab HTTPS origin (since 0.4.23 this plugin no longer touches the Main-default namespace).
- **Where used:** `src/client/remote-settings-scope.ts`, `src/client/index.tsx`.
- **When missing / memory-only:** official `ui-settings` keeps process-local memory mode on non-loopback pages. The plugin then uses the public `remote.settings` describe/mutate RPCs (not a DSH core patch) so the settings page remains writable through `dshlab.noirbright.top`.
- **Upstream:** a public `settingsScope` persistence flag for trusted remote Hosts. Until that ships, keep the Remote adapter and this note.

## Rendering `conversation.plan-review.actions` from a composer takeover

- **Needed for:** restoring the official plan-preview affordance (auto-open of the full plan in the right sidebar plus the manual opener) while this plugin's card replaces the official QuestionComposer in the `conversation.composer` chain.
- **Where used:** `src/client/picker/plan-preview.ts`, `src/client/picker/PlanReviewCard.tsx`.
- **What's missing:** two independent rules block the sanctioned path. The SlotRegistry allows exactly **one declarer per child slot** (`register` throws `slot "…" is already declared`), and official `ui-user-questions` already declares `conversation.plan-review.actions` on its own QuestionComposer entry; separately, `renderSlot` dispatch authorizes against the **rendering entry's own children table** (`SlotOwnershipError`), which a takeover entry cannot obtain. Declaring the key ourselves would therefore throw at registration — in this plugin or in the official panel, depending on load order.
- **Handling:** the card reads the public slot ledger (`slots.entries('conversation.plan-review.actions')`), resolves ui-plan's registered entry by its stable id, and drives its inject face (`openReview` + `hooks.sidebarMounted`). The `dsh-resource://plan-review` address, logged-plan branch, subagent routing, and mounted-session gate all stay inside ui-plan; without ui-plan every operation degrades to "unavailable" and the card keeps working.
- **Upstream:** either allow a shared child-slot declaration (many parents rendering one child list) or publish a `renderSlot`-equivalent that dispatches to any *declared* slot, so a takeover entry can render official child affordances without re-deriving them. Exporting ui-plan's `PlanReviewOpen`/`reviewPreviewAddress` as a supported face would be a narrower alternative.

## Configurable Auto-reviewer model

- **Needed for:** letting a human pin the reviewer model for the official per-call Auto gate (globally and per provider group) instead of always reviewing on the session's own route.
- **Where used:** `src/auto-review.ts` (row `model-switch-auto-review`), `cordis.patch.yml`.
- **What's missing:** `@deepseek-ai/dsh-experimental-auto-review` exports only `name` / `inject` / `apply`; `classifyRisk` hardwires `provider/model` from `header.config` and `dsh-llm` publishes no interception or per-call caller seam ("Requests use raw fetch… no shared proxy or interception configuration"). `GenerateOptions` also carries no effort field, so no effort override exists, and the official gate does not populate `GenerateOptions.sessionId` or `purpose` on its `deepFreeze`d review options.
- **Handling (0.4.25+):** the official `apply` runs unchanged under `ctx.extend({ llm })`, whose wrapper rewrites only `stream()`'s `provider/model` (creating a shallow copy because `classifyRisk` deep-freezes `options`). Immediately after `official.apply(scope)`, `bindAutoReviewSessionCorrelation` registers a `{ prepend: true }` listener on `tools/pre-execute` on the same scope — which Cordis places ahead of the official gate's own prepended listener in the waterfall — and binds `exec.agent?.session` in an `AsyncLocalStorage` scope around `next()`. When `classifyRisk` calls `scope.llm.stream(options)`, the wrapper reads the active session from `AsyncLocalStorage`, derives its current provider (`pending` selection preferred over `lastUsed`, then logged routes), and resolves **provider group → flat reviewer card → session model**. Parallel sessions on different providers therefore review on their own configured models with zero cross-session interference, and mid-session provider switches take effect on the very next review.
- **Upstream:** an official `reviewModel` config (or a route-resolver callback receiving the reviewing session, or populating `GenerateOptions.sessionId` and a review `purpose`) would remove the shadow and waterfall correlation listener.

## Threshold-driven plan-exit compaction (withdrawn in 0.4.21) and send-time switch compaction (withdrawn in 0.4.25)

**Withdrawn in 0.4.21 / 0.4.25:** both plugin-initiated compaction features (`plan-compact` in 0.4.21 and send-time `compactOnSwitch` / `src/switch-compact.ts` in 0.4.25) have been removed from the product. All compaction triggers now belong exclusively to DSH's official compaction engine (`/compact` and automatic pressure/overflow compaction). The record below is kept for historical context.

- **Needed for:** compacting long history with the switched-to model *before* a switched plan approval resumes the session, so the first execution request does not time out.
- **Where used (until 0.4.20):** `src/plan-compact.ts`, `src/capabilities-rpc.ts` (endpoint `plan-compact`), `src/client/picker/PlanReviewCard.tsx`.
- **What's missing:** there is no official plan-exit hook, and the idle-only `compactNow` seam is unusable at plan exit — `exit_plan_mode` awaits `interaction.ask(...)` inside a live tool call, so `agent.phase.kind === 'running'` and `runMaintenance` throws `already has active work`. The turn-safe `compactIfNeeded(agent, 'context-overflow')` (official overflow recovery's own operation, threshold-free with `retainTokens: 0`) is the closest released entry, but its trigger name is semantically "a provider already rejected the request".
- **Handling:** the card asked the Host over this plugin's own RPC before committing anything; the Host measured with `ctx.tokenMeter` (larger of the two envelope prices), compared against the user's threshold, and drove an isolated `compaction-basic` engine pinned to the switched-to route via `compactIfNeeded(..., 'context-overflow')`. Failure kept the Plan pending and retryable; `null` (nothing compactable) proceeded after a notice; threshold 0 disabled. No transcript notices were appended while the ask tool is suspended — the compaction's own durable marker pair and summary replacement are the record.
- **Upstream:** an official pre-plan-exit/pre-answer hook (or a named "manual, turn-safe" `compactIfNeeded` trigger, and/or a public session-level `compactFor(route)` entry) would let plugins express this without borrowing the overflow trigger's name.

## Automatic compaction thrash under sustained pressure

- **Needed for:** predictable official automatic compaction when a session runs above the pressure threshold for hours (long tool-heavy turns).
- **Where used:** observed through the official `compaction-basic` engine (`auto: true`, `_registerAutomaticCompaction` → `agent/pre-step` → `compactIfNeeded(agent, 'pressure')`); this plugin only mounts the same engine with the configured summarization route (row `model-switch-compaction`).
- **What's missing:** once the working set stays above `thresholdTokens` (`thresholdRatio`, default `0.8 × target contextWindow`) and the remaining compactable ranges are small, the official "summary is not smaller than the shadowed content" guard rejects each summary and the engine retries the same range on the *next* pre-step — indefinitely. Session evidence (one working session): 180 `compaction/start` events in ~3 hours, 1–2 attempts per step, 62 rejected summaries, churn active only while the active model's window kept the threshold crossed and silent after a larger-window model took over; identical with this plugin enabled and disabled. Every attempt costs a summarization request and produces a visible checkpoint, so the churn reads as "endless automatic compaction".
- **Handling (no plugin-side change):** per the frozen scope this plugin does not alter compaction policy. User-side mitigations on the forwarded row config: `auto: false` (keeps `/compact`), a higher `thresholdRatio`, a smaller mounted tool schema, or a summarization route whose summaries pass the shrink guard more often.
- **Upstream:** after N consecutive futile compactions (summaries rejected by the shrink guard or reductions that do not cross below the threshold), the engine should back off — skip pressure compaction until the measurement grows by a margin — instead of re-attempting every `agent/pre-step`.

## Preset-internal rows are unreachable by profile patches

- **Needed for:** pinning the compaction summarization route for session compaction, which the Web surface runs inside each agent preset's isolated `compaction` group (`preset-standard`/`preset-ptc`/`preset-cordis` ship their own `compaction-basic` row under `config.plugins`).
- **Where used:** `src/preset-sync.ts` (Host startup bridge), `src/compaction.ts` (row `model-switch-compaction`).
- **What's missing:** `applyEntryPatches` indexes only top-level rows and children of `group: true` rows whose `config` is an entry **array**; a preset row's `config.plugins` list is structurally invisible to patches (an insert targeting the nested group warns `entry "compaction" not found`). Service shadowing cannot substitute: `reflect.provide` throws on a duplicate name and `reflect.set` is owner-fiber only, and preset realms are created registry-side below the root context. The official engine's own config (`summarizationProvider`/`summarizationModel`, priority over the conversation route) is therefore unreachable for preset-nested engines without touching the preset row itself.
- **Handling (0.4.27+):** the Host bridges the nested row at startup instead of shipping copies of the presets: it finds each `@deepseek-ai/dsh-agent-preset` declaring row in the loader, walks the nested entry lists, disables the nested `compaction-basic`, and inserts `model-switch-compaction` after it. An entry that has not started yet gets its raw config replaced; a started entry is reloaded through the public loader `entry.update`; a failure is logged once and the official preset stays mounted. Every other row — including a deployment's own Web-editor preset save — is preserved, and a DSH release that edits its presets needs no re-sync (the 0.4.26 static copies broke every 0.2.1 turn exactly because they pinned 0.2.0 preset content, including the removed `{{cwd}}` persona variable). `minimal` has no compaction group and needs nothing.
- **Upstream:** let patches address rows inside `config.plugins` (index preset lists like group entry-lists), or expose a preset-definition transform hook on `agentPresets.register`, or let `compaction-basic` read a summarization route from a shared settings seam instead of row config. Until one of those ships, the runtime bridge above is the supported path.

## Per-session compaction summarizer route

- **Needed for:** deriving the summarization model per session (provider group → flat compaction card → official row `modelPolicies` / conversation target) while keeping the durable `compaction/summary` record truthful.
- **Where used:** `src/compaction.ts` (row `model-switch-compaction` mounts the official `@deepseek-ai/dsh-compaction-basic` engine under `compactionScope(ctx)`), the settings card `compactProvider`/`compactModel`, and the Provider groups card.
- **What's missing:** the engine resolves its default summarization route from row config (`summarizationProvider`/`summarizationModel`, falling back to `modelPolicies` and the conversation target) rather than a per-session callback. However, `summarizeWithLlm` builds a mutable `GenerateOptions` literal carrying public `sessionId: agent.session.id` and `purpose: 'compaction'`, passes it to `this.ctx.llm.stream(options)`, and then returns `{ provider: options.provider, model: options.model }` to `commitCompactionBody`, which writes that pair into `compaction/summary`.
- **Handling (0.4.25+):** `mountEngine` mounts `BasicCompactionEngine` under `ctx.extend({ llm: compactionLlm(...) }).plugin(...)`. When `options.purpose === 'compaction'` and `options.sessionId` is non-empty, `compactionLlm` looks up the session in `ctx.sessions`, derives its current provider (`pending` selection preferred over `lastUsed`, then logged routes), and resolves `resolveCapabilityRoute(settings, provider, 'compaction')`. When a route is pinned, `compactionLlm` mutates `options.provider` and `options.model` in place before calling `real.stream(options)`, so `summarizeWithLlm` returns and durably records the exact route that wrote the summary. All non-`stream` members (`resolveModelInfo`, etc.) pass through bound to the real `llm` service, and edits to `providerGroups` take effect on the very next compaction with zero engine remounts.
- **Upstream:** a first-class per-session summarization route callback on `BasicCompactionEngine` would remove the need for the `ctx.extend({ llm })` wrapper.

## `llm/stream` cannot substitute options downstream

- **Observation:** `ctx.llm.stream()` dispatches through the public `llm/stream` waterfall (`@deepseek-ai/dsh-llm`: *Waterfall around every streaming model call (retry, replay, routing) … call `next()` to reach the resolved adapter's stream, or yield your own chunks to short-circuit*). The Cordis waterfall contract passes `next()` no arguments — every layer receives the original request arguments and the terminal dispatches the options the call was made with — so a listener may pass through, veto the chain, or short-circuit with its own chunks, but cannot substitute options for anything downstream. A loop-built request also arrives deep-frozen (mutation throws; listeners read it, never rewrite it), and hand-built inputs stay owned by their caller until the stream settles.
- **Consequence for rewrites:** a route rewrite therefore has to sit at the service layer, before dispatch — the pattern both `reviewScope` (`src/auto-review.ts`) and `compactionScope` (`src/compaction.ts`) use: a child context shadows `ctx.llm`, and the wrapper calls the real service directly with the substituted pair, which is the short-circuit that keeps the shadow from re-entering itself.
- **Upstream:** nothing to request for the waterfall itself — its contract (read, or short-circuit with your own chunks) is explicit.

## Auxiliary session-title call moved into the provider (0.2.1)

- **Needed for:** the configurable per-session naming route. The row delegates the actual call to the official auxiliary-LLM package so the durable `session/title-llm-request` record and the request can never disagree.
- **Where used:** `src/session-title.ts` (row `model-switch-session-title`).
- **What changed:** `0.2.1-rc.2` removed `generateSessionTitleWithLlm` and `registerSessionTitleLlmProvider`. The replacement `executeSessionTitleLlm(ctx, config, request, id, prepared)` returns the assembled blocks plus the terminal finish reason and takes the provider's own system prompt, framed input, message seqs, and reasoning-effort selector; `targetWords` / `targetCjkCharacters` moved out of the shared policy into each provider's config (the shared validator rejects them as unknown keys).
- **Handling (0.4.26+):** the row detects the installed line at runtime and mirrors the shipped provider for each: the pre-0.2.1 line keeps the shared call with the targets in its policy, and the 0.2.1+ line builds the official prompt (best-effort line, current-title stability rules anchored on a provider-sourced `currentTitle`), the JSON framing, the least supported reasoning effort, and the official finish/emphasis/empty-output acceptance. `cordis.patch.yml` also disables the `optional-session-title-all-prompts` row that the experimental session-titles bundle inserts.
- **Upstream:** none requested while both lines stay published. A third shape fails closed with `model-switch: … exposes no title call this row understands` instead of guessing. Note for future releases: the shared policy split means a profile row that carries the title-length targets must not forward them into the 0.2.1+ validator.

## Subagent start surface replaced by the activation API (0.2.1)

- **Needed for:** the per-session Subagent route override, which the routed runtime applies by overriding the entry point every delegation tool calls.
- **Where used:** `src/subagent-runtime.ts` (row `model-switch-subagent-runtime` mounts the subclass in place of the disabled `subagent` row).
- **What changed:** `@deepseek-ai/dsh-subagent@0.2.1-rc.2` exports `SubagentRuntime` with `startActivation(spec)` / `waitForChildren(...)` plus a provider registry, and no longer publishes `start(name, request)` or `startContinuable(spec)`. Providers (`dsh-subagent-spawn-in-process`, `dsh-subagent-fork-in-process`) register on `ctx.subagents`, and the composed child options are built inside that package, not at the runtime's public start entry.
- **Handling (0.4.28+):** the adapter recognizes both published lines (`subagentSurfaceOf`) and overrides whichever the installed Host publishes: `start` + `startContinuable` on 0.1.7/0.2.0, `startActivation` on 0.2.1+. The activation spec carries the same `request.parent` / `request.agentOptions` pair, so one resolver serves both lines; every other spec field (`provider`, `label`, `childId`, `signal`, `delivery`) passes through untouched, and the delegation goes through the official prototype method rather than a reimplementation. Only a Host publishing neither surface falls back to the untouched official runtime with one typed startup notice (`routedRuntimeUnavailableNotice`); the setting keeps its stored value.
- **Upstream:** a provider-level delegation hook — or a documented route/agent-options callback on `startActivation` — would let a plugin choose the child route without subclassing the service; a supported subclass seam for the same purpose would also close this gap.

## Auto-review gate dependency list mirrored into the replacing row (0.2.1)

- **Needed for:** the per-session reviewer route override, which wraps the official gate's `tools/pre-execute` listener in an AsyncLocalStorage scope.
- **Where used:** `src/auto-review.ts` (row `model-switch-auto-review`, replacing the disabled `auto-review` row).

The correlation listener binds only after the gate's `apply` actually ran, preserving the prepend order; a duplicate registration still fails loudly.

## Session-title provider slot is single-registration (0.2.1)

- **Needed for:** the configurable per-session naming route. The route override is a naming provider, and DSH 0.2.1's `ctx.sessionTitle.register()` accepts exactly one live registration (a second one throws `session-title provider "<incumbent>" is already registered`).
- **Where used:** `src/session-title.ts` (row `model-switch-session-title`).
- **What changed:** 0.2.1 also ships an experimental all-prompts naming row (`@deepseek-ai/dsh-session-title-all-prompts-llm`, inserted by `dsh-experimental-session-titles-bundle`), which competes for the same slot. Because that bundle's patch layer applies after this plugin's, a static `disabled` cannot reach the inserted row, so enabling the bundle used to fail that row's activation.
- **Handling (0.4.29+):** the row mirrors the official row present in the tree (all-prompts when the experimental row is composed, first-prompt otherwise) and choreographs released loader seams to own the slot: it observes the `loader/patch-context` waterfall, yields its own registration so the official `register()` succeeds (no failed-activation warning), disables the official row through the public `Entry.update({disabled: true})`, and claims the slot back under that row's cadence. A bounded retry plus an initial sweep cover both composition orders.
- **Handling (0.4.43):** a settings write (adding a model provider) re-writes the profile patch and rebuilds the whole composition. The bundle re-inserts that all-prompts row **enabled** while this row is still inside `loader/partial-dispose`, so the slot was still held and the row's own `register()` threw — which aborts the whole composition, so the save failed with `1 entry did not activate … already registered`. The fix releases the slot on the **first** `loader/partial-dispose` of any entry (the earliest observable teardown signal), lets the re-inserted row register, then recovers through the normal disable-then-reclaim path. `loader/entry-init` is also observed as a second chance (it does not fire for every re-insert); nothing is claimed while a live enabled official row is visible.
- **Upstream:** a first-class way to supersede a registered provider — a decorate/replace registration hook, or a multi-provider slot where the newest registration wins — would remove the choreography. Until then the degraded outcome is explicit: the official provider serves naming and one log line says the configurable route is unavailable.

## `permissionPresets.registerAuto` is single-registration with an effect lifetime (0.2.1)

- **Needed for:** the Auto permission preset (`auto` = full-access sandbox + reviewer-approved asks), which the official `@deepseek-ai/dsh-experimental-auto-review` gate publishes through `registerAuto`.
- **Where used:** `src/auto-review.ts` (row `model-switch-auto-review`, replacing the disabled `auto-review` row).
- **What breaks:** `registerAuto(admit)` throws `permission: preset "auto" is already registered` while another registration is live, its disposer is what clears the preset, and `permissionPresets.names` advertises `auto` only while one is live. Two consequences on the plugin side: a re-mounted gate that re-registers before the old effect cleanup runs loses the integration (`auto` disappears from the picker, and a restore fails with `cannot restore preset "auto" without its active integration`); and the gate resolves the presets service's own `sessionProjections` injection on **every** tool call (`permissionPresets.current(session)` is the first `tools/pre-execute` step), so an inactive preset fiber turned every tool call into `cannot get required service "sessionProjections" in inactive context` before its body ran.
- **Handling (0.4.30+):** the row awaits the previous gate fiber's `dispose()` (which settles after its cleanup) before mounting the next gate, and `reviewScope` shadows `permissionPresets` with a defensive face: a failing `current()` degrades to `custom` (the gate skips review and calls `next()`, so the tool body runs), a failing `set()` during teardown is swallowed, and a registration conflict is reported as one log line instead of failing the gate. Degradation is logged once per process, not once per tool call.
- **Handling (0.4.31+):** the registration is now **brokered** (`releaseForTakeover` / `reclaimRegistration`): the row hands the single slot to a displacing row **synchronously** and takes it back without unmounting its gate — disposing the gate is what flips live `auto` sessions to `danger-full-access`, so the sessions' Auto selection is preserved around every displacement. The shadow is always on and resolves the presets service lazily per call, so it protects even while the service is still activating; a `registerAuto` conflict now fails the gate's mount loudly (the takeover retries) instead of leaving an Auto preset that silently does nothing.
- **Upstream:** a replace/unregister API (`registerAuto(admit)` with a documented takeover, or a re-entrant registration that supersedes the previous holder) would let a plugin re-mount without choreographing fiber disposal, and a read-only `isAutoLive()` probe would let the UI tell "preset hidden because no integration" apart from "catalog unavailable".

## Permission selector renders nothing without a settled catalog (0.2.1)

- **Observation:** `@deepseek-ai/dsh-client-ui-permission-presets` returns `null` (the trigger button is not rendered at all) while `catalog === null || selection === undefined` — before the first complete `permissionPresets.catalog()` reply, after a failed reload, or while the session's permission projection has no value. `permissionPresets.names` also drops `auto` whenever its integration is not live.
- **Where used:** the composer, next to this plugin's own picker; reported live as the permission-level button sometimes disappearing.
- **Handling (0.4.30+):** no client-side override — the condition is official UI behavior. Its two causes in this report (catalog reload storms from a flapping Auto integration, and a preset service whose projection read fails) are fixed at their source by the row above, so the selector keeps a settled catalog.
- **Upstream:** a rendered disabled/placeholder state instead of `null`, plus a stable catalog revision while a reload is in flight, would make the selector's absence impossible to misread as a missing capability.

## No supersede seam for a bundled capability row (two layers of `disabled`)

- **Needed for:** keeping one owner on the Auto-reviewer seam when a profile composes both the official `auto-review` row and this plugin's replacing row. A composed official row runs the **unguarded** probe; two live rows also fight over the single `registerAuto` slot, and the loser's effect fails mid-mount (a live failure produced `Auto review of tool … failed … cannot get required service "sessionProjections" in inactive context` for every tool call until the row was disabled and the Host restarted).
- **What's missing:** there is no public "this row supersedes that row" declaration. `disabled` is decided in two layers that do not compose: the profile's own `cordis.patch.yml` (the plugin manager writes `- id: auto-review / disabled: false` there on every toggle) applies **after every bundle layer**, so a static `disabled` shipped by this plugin can never win; and `Entry.update({ disabled: true })` — the only public runtime disable — is **in-memory**, replayed at each startup, not persisted back over the user's patch.
- **Handling (0.4.31+):** the row takes the seam over through the loader's released seams, the same choreography as the session-title provider slot (`src/auto-review-takeover.ts`): on `loader/patch-context` it releases the Auto registration **synchronously before** `next()` (the loader runs the entry's plugin `apply` in the same turn, so an awaited yield collides; a synchronous one lets the official row apply cleanly instead of half-applying), disables the official row through `Entry.update({ disabled: true })`, and re-claims the registration with a bounded retry — preserving live sessions' Auto selection across the displacement. A `loader/partial-dispose` listener re-claims when a re-enabled official row goes away again, and an initial sweep handles rows composed before this one. Toggling the official component back on is therefore caught within one loader cycle and logged; the toggle's persisted state stays the user's, and the takeover simply re-runs (idempotent per entry).
- **Upstream:** one of: a `supersedes: <row id>` declaration applied after all patch layers; making plugin-manager toggles of a row owned by another plugin a no-op with an explanation; or persisting a runtime `Entry.update({disabled})` back to the owning layer so there is a single source of truth for `disabled`.

## `sessionProjections` resolution walks the whole caller fiber chain (0.2.1)

- **Observation:** `internal/get` resolves a service by walking `fiber.store?.[prop]` up `fiber.parent.fiber`; the moment it meets a fiber whose `inject` declares the name while `store` is unresolved (mid-reload, disposed, or blocked on its own dependencies) it throws `cannot get required service "…​" in inactive context`. Twenty-four released rows declare `sessionProjections` in `inject` (`dsh-permission-presets` itself, `dsh-session-title`, `dsh-plan-mode`, `dsh-token-meter`, `dsh-tool-todo`, `dsh-agent-loop`, `dsh-working-directory`, …), and `permissionPresets.current(session)` — the first `tools/pre-execute` step of the Auto gate — resolves it through the **caller's** chain on every tool call. Any one of those rows reloading during a plugin-manager write, a bundle toggle, or a plan-mode switch can therefore fail that read.
- **Consequence:** while a mid-chain fiber is inactive, an **unguarded** probe turns every tool call into the raw service error before its body runs. This is the recurring outage behind the live reports; what varies between occurrences is which row was mid-reload (the trigger this time: the plugin manager's patch write at 15:22:34 re-enabling the official `auto-review` row, which re-applied a chain of entries around it).
- **Handling (0.4.31+):** this plugin cannot change Host lifecycle, so it removes its exposure instead: the official unguarded gate is never left running beside this row's (takeover above), and this row's own gate resolves the presets service through the always-on shadow, which degrades the probe to `custom` — the tool body runs — and logs the failure **once with the exact fiber chain** (`uid/state/name/inject` per fiber), so the next occurrence names the inactive fiber instead of guessing.
- **Upstream:** `permissionState()` should resolve `sessionProjections` from the **presets service's own** fiber (its `inject` already declares it) instead of the traceable caller's chain, or gate resolution should skip fibers whose `store` is not yet resolved when a further-up parent provides the name. Both keep the tool path free of neighboring rows' reload windows.
